# expert2skill 访谈脚本设计稿 v0.1

> 用途：expert2skill skill 的核心流程——通过自然语言对话，把专家（非 AI 背景）的隐性方法蒸馏为结构化规则库。
> 状态：设计稿（尚未开发），作为未来 `references/interview-guide.md` 的雏形。
> 设计原则：
> 1. **专家不懂 schema，AI 负责翻译**——专家只说业务语言，AI 负责映射到题型/字段。
> 2. **渐进确认**——每阶段产出小结果，专家确认后再进下一阶段，避免一次性大输出压垮对话。
> 3. **示例脚手架**——每个提问附业务示例（用素材库），降低专家表达门槛。
> 4. **反例优先**——人最容易说清"什么不行"，再从反面推导"什么算行"。

---

## 访谈总体流程

```
P0 适配性判断 ── 不适合 → 诚实告知，转咨询型 skill 建议
   │ 适合
P1 领域与对象定义
   │
P2 维度拆解（→ categories）
   │
P3 逐项蒸馏（→ items + judge + 阈值）   ← 最重，循环执行
   │
P4 条件触发与开放题（→ conditional/text/self_check）
   │
P5 权重与汇总确认（→ 生成 rule_library JSON）
   │
P6 打包与验证（→ skill 包 + 试跑 evaluate）
```

---

## P0：适配性判断（5 个问题内）

目标：判断专家的方法是否适合规则引擎。不适合就尽早止损。

**提问模板**（AI 用示例引导，专家只需回答是/否或简单描述）：

| # | 问题 | 判定 |
|---|------|------|
| 1 | "您的方法，通常是**评估/判断**一个对象（比如评估一家公司、检查一辆车、判断一个申请），还是**生成**一个东西（比如写文案、做设计）？" | 生成型 → 不适合规则引擎 |
| 2 | "您做判断时，心里有没有**明确标准**？比如什么情况**一定不行**？" | 完全没有标准 → 不适合 |
| 3 | "如果让您对评估对象**打分或分等级**，您觉得自然吗？（比如优/良/中/差，或 0-100 分）" | 很抗拒打分 → 不适合 |
| 4 | "您评估一个对象，一般会从**几个方面**看？大概能列出几个？" | 少于 2 个方面 → 可能太笼统 |
| 5 | "如果让 AI 按您的标准**逐条问您**，您愿意把标准一条条讲出来吗？" | 不愿/嫌麻烦 → 时机不对 |

**通过标准**：1=评估型，2=有标准，3=能接受打分，4=≥2 个方面，5=愿意。全部满足 → 继续；否则转"咨询型 skill"建议（用户可另行选择做对话式专家包）。

> 边界情况：部分规则化——如股票投资中"情绪判断"不可规则化，P0 通过但需在 P4 标记"开放题/不可规则化部分"，诚实告知专家。

## P1：领域与对象定义（4-5 问）

目标：确定 `rule_library` 的元数据：id（slug）/ title / 评估对象 / 结论形态 / authority。

| # | 问题 | 映射字段 |
|---|------|---------|
| 1 | "这套方法在您行业里叫什么？（显示名）" | `title`（中文显示名，如"营养状况评估"） |
| 2 | "给它起一个**英文短标识**（slug）会是什么？用于文件名/命令。若您想不到，我根据显示名建议一个（如 nutrition-assessment）" | `id`（kebab-case 小写） |
| 3 | "它评估的**对象**是什么？（公司？项目？人？设备？）" | 结论描述用 |
| 4 | "最后给出什么**结论**？（分数？优/良/中/差？通过/不通过？推荐/不推荐？）" | 决定 scoring 与报告形态 |
| 5 | "这套方法是您自己总结的，还是基于某套公开标准/方法论？" | `authority`（含出处） |

**命名规则**（AI 辅助建议，专家确认）：
- `title`：中文显示名，用于界面/报告标题；建议 ≤12 字，含"评估/检查"等动作词。
- `id`（slug）：kebab-case 小写英文，只能 `[a-z0-9-]`；AI 从显示名音译/意译生成候选
  （如"营养状况评估"→ `nutrition-assessment`），专家可改。
- **前缀**：本地使用时保持干净 slug（无前缀）；**上架发布时统一加 `ch-` 前缀**
  （如 `nutrition-assessment` → `ch-nutrition-assessment`），由打包器 `--publish-prefix` 处理，
  访谈阶段不涉及。

**AI 动作**：确认后，用一句话复述："我理解您的方法叫「title」，标识是 `id`，用来评估「YY」，最后给出「ZZ」结论，依据是「WW」。对吗？"

## P2：维度拆解（一次对话完成）

目标：得到 categories（评估维度）。

**提问模板**：
> "您评估一个 [对象] 的时候，会从哪几个**大方面**看？请列出 2-6 个，每个用一句话说清楚'看什么'。比如评估一家公司，您可能看：财务健康、估值、护城河、风险……"

**追问技巧**（专家说不出时）：
- 用素材库示例："参考别人的做法，比如同花顺问财会把选股分成基本面、技术面、资金面。您的做法会怎么分？"
- 用反面："有没有什么情况，您一看到就直接判'不行'？这属于哪个方面？"

**产出**：`categories[]`（id: A/B/C…, name, 一句话 description）。AI 逐条复述确认。

---

## P3：逐项蒸馏（核心，每维度循环）

目标：每个 category 下的 items 及其题型、判定条件、阈值、evidence。

**每维度提问流程（4 步）**：

### 步骤 3.1 挖判定项
> "在「[维度]」这个方面，您会**看哪些具体点**？比如看财务健康，您会看 ROE、负债率、现金流……您通常会检查哪几项？"

产出：该维度的候选 item 列表（仅名称 + 一句话说明）。

### 步骤 3.2 定题型与阈值（用"反例→边界→及格"三步）
对每个候选 item：
> ① "什么情况算**明显不行**？（比如 PE > 30 算贵？ROE < 8% 算差？）" → 得到 `fail_condition` 和初步数值
> ② "什么情况算**刚好及格**？（比如 PE 在 20-30 算勉强？）" → 得到 `partial_condition`
> ③ "什么情况算**好**？" → 得到 `pass_condition`

**AI 自动推断题型**：
- 专家给出数值阈值 → `numeric`（如 PE、市值）
- 专家说"好/中/差"档 → `scale`（如 ROE：≥15 好 / 10-15 中 / <10 差）
- 专家说"有没有 X" → `binary`（如是否 ST、是否有止损）
- 专家说"看有没有 X、Y、Z 里几个" → `multi_select`（如护城河类型）

**默认值建议**：专家迟疑时，AI 给公开口径默认值（如 PE 20/30、股息率 3%、ROE 15%），专家只需"调高/调低/可以"——大幅降低建模负担。

### 步骤 3.3 挖 evidence（证据要求）
> "您判断这一项时，需要看到什么**材料或数据**？截图？文件？数字？" → `evidence_required: true/false`

### 步骤 3.4 挖 recommendation（不通过时的建议）
> "如果这一项不通过，您一般会建议对方**怎么做**？" → `recommendation`

**循环控制**：每维度完成后，AI 汇总该维度 items 让专家过目："您看财务健康这个维度，我整理出 3 项：ROE 持续性、自由现金流、负债率，阈值和判定如下……对吗？还有什么要加或改的？"

---

## P4：条件触发与开放题（一次对话）

目标：conditional / text / self_check 题型。

### 4.1 条件深挖（conditional）
> "有没有什么情况，是**某个答案命中后您会进一步追问**的？比如负债率过高时，您会再看短期借款占比？" → `applies_when` + conditional item

AI 需确认触发条件引用方式（`value >= X` 或 `result == 'fail'`）。

### 4.2 开放问题（text）
> "有没有哪些点，**不是数值能表达的**，需要对方用文字描述、由您来经验判断的？比如'这家公司的护城河到底多强'？" → text item

**铁律**：开放题必须配 `judge.mode = "expert_review"`（由评估者自评，AI 不自动判分），或挂一个客观锚点题。

### 4.3 自问自检（self_check）
> "您每次做判断前，会不会**问自己一些问题**？比如'我是不是在自欺'、'我能列出不买的理由吗'？" → self_check item

若专家说不出，AI 给出通用自检示例（如"反方证伪：找出 3 个反对理由"）。

---

## P5：权重与汇总确认

### 5.1 权重
> "这几个维度（或这几项），哪个**最重要**、哪个次之？" → 权重赋值
- 建议采用相对权重：最重要的设为 2，普通的 1，次要的 0.5
- 一票否决项（P2 追出的"直接判不行"）权重置高或标注 `critical` severity

### 5.2 生成 JSON
AI 汇总生成完整 `rule_library` JSON（结构见 `value-investor.rules.json` 样例），**逐维度展示给专家确认**，重点确认：题型是否理解正确、阈值是否准确、applies_when 是否合理。

---

## P6：打包与验证

1. 生成 skill 包（复用 build 模式：SKILL.md + scripts/*.py + package.json + _meta.json）
2. 用 2-3 个真实案例试跑 evaluate，专家核对结果
3. 迭代至专家满意

> 第一批不涉及云端（`/api/v1/libraries` 属后续阶段），此处不再提供上云注册步骤。

---

## 关键约束与铁律

1. **AI 永不替专家做判断**——只帮专家把判断翻译成结构；专家确认是唯一权威。
2. **开放题永不自动判分**——expert_review 模式下 AI 只辅助展示描述，不猜测结论。
3. **不可规则化的部分诚实标记**——不要硬塞，建议转咨询型 skill。
4. **一次确认不超过 5 项**——防止认知过载；大维度拆成多轮。
5. **外部素材须标注来源**——规则库 `authority` 或 item 的 `ref` 记录出处（如"同花顺问财公开口径，2026-08"）。
6. **每阶段有产出物**——P0 通过与否 → P1 元数据 → P2 categories → P3 items → P4 特殊题型 → P5 JSON → P6 包。任何阶段可回退重来，不丢已确认内容。
